# AIJADE implementation and evidence rules

- Implement requested product capabilities independently within AIJADE's existing .NET runtime, server state and channel adapters. External projects and videos are references for design, interfaces and failure cases. Do not copy or mechanically translate their implementation, install their complete plugin packages, or create a second plugin host as a shortcut.
- Keep third-party source-reading snapshots, video/audio, transcripts and comment bodies out of public deliveries. Record source URLs, fixed revisions, reading scope and hashes; use original summaries. Character images, voices and other assets need their own provenance.
- Distinguish character continuity from audience visibility. Preserve explicit private Web/QQ binding and keep private material out of group contexts. A shared character does not authorize shared private history.
- Verify product changes through the actual affected flow. Keep synthetic platform/model fixtures distinct from live QQ, browser, hardware and scientific acceptance.
- Preserve historical research packets, source freezes, raw outcomes and failed attempts. A later product build does not inherit a previous experiment's qualification. Use the pinned historical snapshot for historical verification and test current product code separately.
- On this Mac, every AIJADE working file, environment, cache, model, log, worktree and deliverable must stay under `/Volumes/Untitled/AIJADE/`. Use an explicit directory inside that root and project-local temporary/cache configuration. Existing general SDKs and installed tools may be read where installed.

The November 16 reference review and the independent implementation backlog are in `docs/VIDEO-REFERENCE-ADOPTION.md`.
