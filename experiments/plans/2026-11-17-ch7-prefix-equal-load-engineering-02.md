## Candidate implementation and authentication contract

The journal optimization keeps every actual old-prefix read and exact byte
comparison, with independent inner/outer incremental parsing and rolling SHA.
Detached snapshots and permanent poison after partial failures remain intact.
It is not constant complexity: reads/comparisons and snapshots still grow.

Two additional fixed-cost changes form one candidate. Only the standard-library
identity-ready shim is launched with `-S -B`; its target argv/env, execve, ready
clock, held-gate double kernel-birth witness, wait and deadlines are unchanged.
Controlled marker tests show the target Python still loads its normal venv,
site and psutil after execve. The parent interpreter is unchanged. No target
program is prewarmed and no first-use refusal is relabelled.

Only the two policy-bound live daemon executable paths use the new
`BinaryAuthenticator`. The first actual snapshot reads and hashes each complete
file before approving immutable bytes. Each subsequent call still opens with
O_NOFOLLOW, checks a regular file, reads the entire actual file to EOF and
compares all bytes. A cached SHA is returned only for exact equality to the
approved bytes. A stable change/truncation/growth produces the current actual
SHA from the same physical read, without approving the changed baseline. Read
exceptions and before/after/current device/inode/size/mtime instability retain
the original refusal. No inode/mtime-only cache, skipped read, or process PASS
cache is permitted. Non-daemon source/helper/shim hashes keep the cold method.
The policy pins the new module SHA; current, raw and policy pin must all agree.

There is one authenticator per controller, only on the live inner path. The
outer journal replay remains independent and never borrows the producer state.
Construction binds paths/SHA only and does not read daemon contents. Initial
hashing and baseline allocation occur inside the first measured snapshot.
The per-file cache cap is 128 MiB; the total retained-content cap is 192 MiB.
An over-cap file still receives a full streaming SHA with no byte cache. These
are cache payload caps, not input-read caps or RSS limits. The saved file sizes
are 59,795,424 and 78,301,616 bytes: 138,097,040 bytes of persistent content for
this single instance, plus object, allocator and transient memory. Two snapshots
still read 276,194,080 actual file bytes per tick. Memory/RSS is measured, not
inferred from the payload cap. Statistics count attempted work, including failed
calls; they do not alone prove completed authentication or less I/O.

The actual native artifact remains the byte-identical, previously prepared
AIJADE helper at its original path. This holds preparation identity constant;
it is not an installation-cold-start claim. Its actual byte/source hashes and
all full raw payload/argv/identity/wait rules remain mandatory every invocation.
The existing-system-process and real-pipe small controls cannot substitute for
the actual native population below. Combined changes are engineering candidates;
no single-component causal speedup is claimed from the short refused run.
