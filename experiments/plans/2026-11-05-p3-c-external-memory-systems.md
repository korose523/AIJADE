## Study information

**Research question.** What does the pre-check proposed in the paper (§6.1) find, and fail to find, when applied to memory systems other than the authors' own kernel?

**Hypotheses.** None. Neither the number of systems in which a diagnostic is marked nor its direction is specified in advance.

## Design plan

**Study type.** Diagnostic measurement on existing open-source software, on a public corpus.

**System selection rule (fixed now).** A system is included if it (1) is open source; (2) runs on the authors' machine; (3) ranks by more than one score component for most questions, or applies a threshold, penalty, filter or eviction that can remove or demote any scored item, and these components or steps can be read out, switched off or replaced (without them, steps 1 and 3 of the pre-check have nothing to compare); (4) lets the same candidate pool be re-ranked; and (5) can ingest LoCoMo. The four parts of the selection are stated separately.
- *Eligible systems.* Every system that meets the rule; those that do not are listed with the rule they fail. The frame is the desk check below together with the reading of 5 November 2026 (`experiments/memory/scorer-survey.json`, 21 systems at pinned commits). Rule (5) has not been checked for the systems added by that reading.
- *Two strata (proposed 5 November 2026).* Stratum A: a time term is added to relevance with no normalization over the candidates. These are CrewAI's default recall, LangChain's `TimeWeightedVectorStoreRetriever` and LlamaIndex's `TimeWeightedPostprocessor`. Stratum B: every other eligible system. All of the earlier order lies in stratum B (Mem0, Graphiti and MemOS have no time term in the score, MemoryOS has one only in eviction, Generative Agents normalizes), so without stratum A the first two steps of the pre-check would never meet the form that the paper studies, and a clean result would not show whether the pre-check can detect it.
- *Qualification order.* Stratum A: CrewAI, then LangChain's retriever, then LlamaIndex's postprocessor. Stratum B: Mem0, MemoryOS, Generative Agents, then MemOS for step 3 of the pre-check only (it ranks by a single effective component in its default configuration, so steps 1 and 2 have nothing to compare, but its filter acts after scoring), then Graphiti if the cost of its graph-database setup is agreed. A system whose stored items cannot be mapped to their source turns fails qualification for the recall comparison.
- *Systems that must be completed.* Two, the first that qualifies in each stratum. A system that must be completed completes the full write and retrieval runs with all the steps of the pre-check that apply to it.
- *Stopping rule.* After the first system is completed, each further system is attempted in order until the P3-C window of plan v0 (18 January to 12 February 2027) ends, or until a system's installation and qualification take more than 2 person-days, or a system needs a paid service whose cost has not been agreed; the system is then reported with the stage it reached, and the systems after it as not attempted.

Conclusions are written only about the systems and the pre-check steps actually completed, each named. Whether the descriptive marks fall on stratum A rather than stratum B is described and not tested: there are too few systems for inference.

**Desk check (completed 23 October 2026 by reading each repository's source; nothing installed or run).** Mem0 (additive semantic + sigmoid-normalized BM25 + entity boost over a semantic pool), MemoryOS (similarity ranking with thresholds; an unnormalized heat score decides eviction), Generative Agents (min–max-normalized recency, relevance and importance, weighted 0.5/3/2) and Graphiti (cosine + BM25 fused by reciprocal rank) meet the rule; MemOS meets it only through its filtering step, as it ranks by a single effective component in its default configuration; A-MEM ranks by vector similarity alone, using links only to add neighbors, and fails rule (3). Letta and LangMem were checked the same way on 29 October 2026 and also fail rule (3) on the authors' machine. Letta's current source (letta-code, commit `a8900b8`) ranks past messages by BM25 in its local backend, adding a constant for each quoted phrase of the query (16 of LoCoMo's 1,986 questions contain one) and down-weighting only the conversation's latest user message and search echoes; it delegates vector and hybrid search to the Letta API server, whose code is not in the repository, and its retired Python server fused vector and full-text ranks by weighted reciprocal-rank fusion only through a hosted vector service. LangMem (commit `ae6f15f`) ranks by the vector similarity of the LangGraph store, over memories extracted by an LLM. Graphiti is attempted only after the other systems, as its graph database is the largest setup. Each included system is installed from the commit recorded in `experiments/memory/scorer-survey.json` (CrewAI `24c686d82f1f`, LangChain `b4aa7e7d00c4`, LlamaIndex `444fdf068470`, Mem0 `ed1f10fc8708`, MemoryOS `587ed7755c7a`, Generative Agents `fe05a71d3e4e`, MemOS `d326a6419467`, Graphiti `fb60e59d4a20`).

**Pre-check (identical to §6.1).**
1. On the same candidate pool, `recall@K` of ranking by relevance alone against the system's own ranking.
2. The mean number of the top K items newer than the question's newest evidence turn, against its unbiased expectation.
3. Switching off, one at a time, each penalty, threshold or filter that acts after scoring (for example MemoryOS's heat-based eviction), and measuring delivered `recall@K` again.

**Applying the pre-check to another system (fixed now).** The candidate pool is the system's own set of candidates before its final ranking (its whole store if it scores every item), and the share of questions with a gold item in the pool is reported, as in the paper (§4.2). Relevance alone is the system's own embedding similarity between question and item. An item derived from several turns counts as a hit on each of them, as a distilled fact does in the paper, and its time is that of its newest source turn in the corpus, not the system's clock. Because such items make a hit easier, each system's report states its stored unit (turn, message batch, extracted fact or summary), the length of its items (characters: median, quartiles and maximum) and the number of source turns per item (median and maximum). Steps 1 and 2 work on the pool in the micro caliber (hits pooled over questions), as the paper's diagnostic track does: in step 1 a threshold of the system is applied to both arms by the system's own score, as the paper applies its floor; step 2 counts within the top 8 of the system's own ranking before any threshold, and its unbiased expectation is computed as for the paper's Table 1, eight times the share of the dialogue's turns not older than the question's newest evidence turn, taken over the stored items when they are not the turns. Step 3 uses the system's delivered results in the macro caliber (the mean of the per-dialogue recalls), as the paper's delivery track does. Every `recall@K` is reported with its caliber.

**The clock (fixed now).** A system that reads the wall clock at retrieval receives creation times shifted by one constant per dialogue, so that the dialogue's last turn was written at the time of the read and every age within the dialogue is kept. Without this every item would be years old and a time term could not act.

**Writing the corpus (fixed now).** Each dialogue is written into a fresh store in turn order through the system's own interface for adding conversation messages, with the speaker as the message's author where the interface has one. Where the system's repository has its own LoCoMo evaluation, its way of writing (batching and fields) is followed; otherwise one turn is written per call. Where a system accepts a creation time, it is the time the kernel's loader assigns (`src/Aijade.Memory/Locomo/Locomo.cs`: the session's date and time plus one minute per turn); otherwise the system's own clock is used and recorded. Questions are posed after the whole dialogue is written. A system that writes through an LLM writes each dialogue once; the variance of that writing is not estimated and is reported as a limitation.

**Reading (fixed now).** The pre-check yields two observed quantities, each reported under its own name with its interval: (a) the change in `recall@8` relative to ranking by relevance alone, and (b) the number of top-8 items newer than the evidence relative to its unbiased expectation. A change in (a) by more than a factor of 2, or a value of (b) above 1.5 times the expectation, is marked as a descriptive diagnostic, not as a verdict; with a baseline of zero the ratio is reported as not available. Both quantities describe the ranking. A statement about comparisons of memory policies is made only for a system in which the difference between the effect of the scoring convention and the effect of a policy is estimated directly, with an interval. Both effects are measured per dialogue on delivered `recall@8` (macro): the scoring effect as the system's own ranking minus ranking by relevance alone, the policy effect as one of its memory policies (for example MemoryOS's heat-based eviction) switched on minus off. Each is reported with its sign and its interval, and the quantity compared is D = |scoring effect| − |policy effect|, with a conversation bootstrap interval. The sentences each result allows are fixed now: if the interval of D lies above zero, "in this system the scoring convention changed delivered recall@8 by more than the policy did", with both effects and their directions; if it lies below zero, the same sentence with the two effects exchanged; if it includes zero, "the two effects were not distinguished on this corpus". No other statement about policy comparisons is made.

## Sampling plan

**Existing data.** LoCoMo (ACL 2024 release, SHA-256 `79fa87e90f04081343b8c8debecb80a9a6842b76a7aa537dc9fdf651ea698ff4`), the same corpus as the paper; the 1,540 answerable questions are primary, all 1,986 reported alongside. **Sample size.** All 10 dialogues; the conversation is the unit of resampling.

## Variables

**Measured.** Per system: the stored unit, item lengths and source turns per item; the pool's coverage of gold items; the three pre-check quantities at K = 8 (and K = 1, 2, 4 as description); the two diagnostic marks; where estimable, the difference between the scoring-convention effect and a policy effect (defined under Reading).

## Analysis plan

**Statistical models.** Conversation bootstrap (10,000 resamples, percentile 95%) and exact sign-flip test for the paired differences, as in the paper; the interval of a ratio is taken from the same resamples.

**Inference criteria.** A system in which no problem is found is reported in the same detail; the paper's external-validity statement is written only about the systems actually checked.

**Data exclusion and missing data.** Questions whose evidence turns cannot be located in a system's store (for example after its own summarization) are counted and reported per system, and hit rates are given with and without them.

## Other

**Plan and record.** This plan is committed on its own before its code is written. Results are written under `experiments/p3-c/`.

**Resources.** Installing each system needs downloads (packages, embedding models; permission per system). Systems that write memories through an LLM are run with one local model at temperature 0 through an OpenAI-compatible endpoint, and systems whose default embedding model is hosted with one local embedding model: the embedding model is nomic-embed-text v1.5 (manifest SHA-256 `0a109f422b47e3a30ba2b10eca18548e944e8a23073ee3f3e947efcf3c45e59f`); the language model is `qwen2.5-coder:7b-instruct` (the Mac holds no llama3.1:8b), and it is used only where a system cannot write without one. A system that offers to write without a language model (explicit fields, or no inference) is written that way, which is recorded as a deviation from its default, because one pass of 5,882 turns through a local model is not practical on the Mac. Replacing a system's default hosted model is recorded as a deviation from its default configuration. A paid API is used only with the advisor's agreement on cost.
