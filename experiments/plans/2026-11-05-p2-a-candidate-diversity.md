## Study information

**Research question.** On tasks chosen by the rule below from a public benchmark, so that first candidates are not settled in advance, how large are the verifier's error rates (`hallucinationRate`, `missRate`) and predictive values, and how far do they differ from those measured on the existing bench, whose unusable skills are 13 distinct programs in 7 tasks? The answer is the difference of each rate from the existing estimate with its 95% interval; no judgment of similarity or agreement is made.

**Hypotheses.** None directional; the existing direction (lenient for the 7B model, not established under task resampling) is what is being re-examined.

## Design plan

**Study type.** Experiment with LLM-generated programs judged against a deterministic execution oracle.

**Task sets.** Before any generation, the ported tasks are split by a fixed seed `[DECIDE WITH ADVISOR]` into development tasks (`[DECIDE WITH ADVISOR: e.g. 20%]`) and a selection pool. The difficulty pilot (stage 2) runs on both; the verifier pilot of stage 3, if run, uses development tasks only; task selection (stage 4) and the main run (stage 5) use the selection pool only. No development task enters the main run, so no verifier output that shaped the design is part of an estimate. Decoding is greedy, so on a selected task the main run's first candidate is the difficulty pilot's: the pilot's oracle outcomes on the selection pool select on usability (stage 4), and this is why the results are stated for the tasks the rule selects.

**Stages (each completed and reported before the next starts).**
0. *Compatibility check (no generation).* Candidate public task sources `[DECIDE WITH ADVISOR: e.g. EvalPlus HumanEval+ and MBPP+]` are checked for whether each task can be decided completely by deterministic tests in the existing JavaScript (Jint) executor or needs a Python executor. Only fully decidable tasks are ported. *Status (2026-10-25): a static screen was run before registration and involves no generation and no outcome data. It is code commit `629187a`; the result is `experiments/p2-a/evalplus-compatibility.json`, archived in `586d6c3`. Against the oracle's exact structural equality, and taking account of EvalPlus's enforced float tolerance and special oracles, it classes HumanEval+ (164 tasks) as 117 direct, 24 with caution, 8 needing a comparator change and 15 incompatible; MBPP+ (378) as 308, 10, 34 and 26. The source to use, whether to add tolerance or set-equality comparison, and whether to exclude the incompatible tasks are decided with the advisor before stage 1. Expected outputs still require running the canonical solutions.*
1. *Existing translations.* MultiPL-E (F. Cassano et al., IEEE Transactions on Software Engineering 49(7), 2023, DOI 10.1109/TSE.2023.3267446) translates HumanEval and MBPP into other languages, JavaScript among them. Whether its JavaScript tasks can be used, and how they align with the extended inputs of HumanEval+ and MBPP+, is checked first. If they cannot be used, the reason is recorded and the tasks are ported here; expected outputs come from running the canonical solutions in an isolated environment and are never shown to the verifier. *Status (2026-10-29): a desk check read MultiPL-E's public repository (commit `3025a53`) and its Hugging Face dataset card; nothing was downloaded or run. Its JavaScript sets hold 161 HumanEval tasks (HumanEval/32, 38 and 50 are not in its source files) and 397 MBPP tasks, and it has no JavaScript translation of HumanEval+ or MBPP+. Its tests are base tests only: a task is translated only if every assertion has the form `left == right`, and in the two source files read (HumanEval/2 and 4) the original tolerance comparisons were replaced by exact comparisons on other inputs. The tests run under Node's legacy `assert.deepEqual`, which compares primitive values with `==`, and Python's `None` becomes `undefined`; both are looser than the oracle's exact structural equality. Its translated prompts (a JavaScript signature with the docstring as comments) can therefore serve as task statements, but its tests cannot serve as the oracle, and the extended inputs of HumanEval+ and MBPP+ still have to be translated here. Against stage 0, the 161 tasks contain all 117 direct HumanEval+ tasks, and its 400 MBPP source tasks contain 356 of the 378 MBPP+ tasks, 305 of the 308 direct ones; which three of the 400 failed the JavaScript translation can only be seen in the data. Its repository licence is BSD-3-Clause with a clause forbidding use as training data, while the dataset card says MIT. Whether to use its statements is decided with the advisor.*
2. *Difficulty pilot (generation only, no verification).* On every ported task (both sets), the main model generates one candidate per task at temperature 0, and candidates at temperatures 0.4 and 0.8 with fixed seeds; the oracle alone measures whether the first candidate is usable and how often distinct candidates arise. The pilot does not run the verifier and is not called a calibration pilot.
3. *Precision design.* A separate pilot that runs the verifier, or a precision scenario fixed in advance, sets the number of tasks N, trials T and minimum exposure per task q for the primary measure: the false-pass rate (`hallucinationRate`) of the main model with template A, self-verification on and feedback on, with a task-clustered 95% interval `[DECIDE WITH ADVISOR: percentile or BCa]`. Target: larger half-width max(estimate − lower, upper − estimate) of that interval at most `[DECIDE WITH ADVISOR: 0.15]`. In the existing main run this cell gives 33/85 = 0.388 with the percentile interval [0.143, 0.846] (larger half-width 0.458); over both feedback conditions the rate is 59/139 = 0.424 with the BCa interval [0.060, 0.769] (0.364). In both, the unusable skills come from 7 tasks. Scaling by the square-root rule to a half-width of 0.15 suggests about 65 tasks with unusable skills for the first and about 41 for the second; derived from intervals over 7 tasks, these are budgeting assumptions, not design values. What the design fixes, in this order:
   - **M**, the number of selected tasks with at least one unusable skill that the target needs, from the verifier pilot or the scenario;
   - **N**, the number of tasks to select, N = ⌈M / p⌉, where p is the share of selected tasks that yield an unusable skill. p is estimated in the difficulty pilot on the development tasks; the planning value until then is the existing bench's 7/44 ≈ 0.16, which gives N ≈ 258 for M = 41 and N ≈ 409 for M = 65, against 425 tasks that stage 0 classes as direct and about 340 in the selection pool at a 20% development share. With the re-scored labels of the re-tally below (39/115, BCa interval [0.000, 0.760], larger half-width 0.421, unusable skills from 5 tasks), the same arithmetic gives M ≈ 39 and, with p = 5/44, N ≈ 344. N cannot exceed the tasks of the selection pool that the rule of stage 4 keeps; if the computed N is larger, N takes that number and the half-width expected there is reported with the design;
   - **q**, the minimum number of slots per task in one round (each slot runs in all four cells; the existing mean is 360/44 ≈ 8.2), `[DECIDE WITH ADVISOR: e.g. 8]`;
   - **allocation**: each trial draws 12 tasks, as in the existing runs, but in a balanced order (a permutation of the N tasks fixed by the master seed, taken 12 at a time and repeated), so that every task gets ⌊12T/N⌋ or ⌈12T/N⌉ slots per round. The condition 12T ≥ qN alone is only a budget; this order is what makes every task reach q;
   - **T**, the number of trials, the smallest with ⌊12T/N⌋ ≥ q (for N = 258 and q = 8, T = 172 instead of the existing 30);
   - **calls**: in the existing main run 7,200 slots (30 trials × 12 tasks × 4 cells × 5 rounds) took 1,621 live generations and 871 verifier replies, about 0.35 calls per slot; at that rate one template's run needs about 0.35 × 240T calls (about 14,000 for T = 172), and the rate measured in the pilots replaces it. If the calls exceed the budget `[DECIDE WITH ADVISOR]`, N is reduced first and the half-width expected at the reduced N is reported with the design; the target is not changed after the results.
4. *Task selection.* Tasks whose pilot candidates are all usable or all unusable are not selected; the full list and the rule are archived. This rule changes the mix of usable and unusable skills: the predictive values depend directly on it, and the false-pass and false-fail rates may change with it as well. Results are therefore reported as values on the tasks selected by this rule, with the predictive values and the base rate; if only tasks of middle difficulty are selected, the scope of generalization says so.
5. *Main run, on a qualified device only.* The existing design with the numbers of stage 3: 2×2 (self-verification × environmental feedback), T trials of 12 tasks in the balanced order, 5 rounds, master seed `[DECIDE WITH ADVISOR]`, verifier templates A and B both run. It starts only after the device qualification of README rule 6. If a task does not reach q slots (for example after a sandbox-level error), it is reported with its count and kept; if too few tasks yield unusable skills, the shortfall in precision is reported and tasks are not added after the fact.

**Calling rule and test audit (added 4 November 2026).** A re-tally of the recorded runs (`experiments/rq-c/oracle_audit.py`; exploratory, made after the results were known) found that the sandbox's rule for finding the function, which the verifier's prompt does not state, and one test case that the instruction does not determine account for 20 of the main run's 59 false passes. Therefore, before stage 2: (a) the generation prompt, the verifier prompt and the sandbox use one calling rule, which both prompts state, and the sandbox also resolves a single top-level `const` or `let` binding, as an option whose default keeps the archived behavior, so that the archived runs still replay; Chapter 5's regression is re-run on the change and recorded in `docs/STATUS.md`; (b) every test case of the ported tasks is read against its task statement by the first author before any model output is seen, and cases the statement does not determine are removed and listed; (c) the reverse check (test-failing candidates against the statement) is run on the main run and reported beside the differential test. The comparison with the existing rates is made with the recorded estimate (59/139 = 0.424) and with the re-scored one (39/115 = 0.339), each with its interval.

**Blinding.** None (automated).

## Sampling plan

**Existing data.** The pilot's outputs are used only to select tasks and size the run; the main run's estimates come from new generations.

**Sample size.** Fixed in stage 3 by the rule above; recorded and pushed before stage 5 starts.

## Variables

**Measured.** Per judged skill: self-verdict, execution outcome; per distinct (task, code) candidate: the same.

**Indices.** `hallucinationRate` = FP/(FP+TN), `missRate` = FN/(FN+TP), false discovery and false omission rates, counted by skill and by distinct candidate.

## Analysis plan

**Statistical models.** As in the paper (§5): task-cluster bootstrap (percentile and BCa) intervals; Wilson intervals as a description; `missRate − hallucinationRate` with its task-bootstrap interval.

**Reporting.** Side by side with the existing results, not pooled: for each rate, the estimate on the selected tasks, the existing estimate, and their difference with a 95% interval from independent task resamplings of the two runs.

**Inference criteria (fixed in advance).** If the direction is opposite to the existing one or the interval of the difference includes zero, the paper's statements about the direction are reworded on the new result.

**Data exclusion.** Verifier replies not beginning with PASS or FAIL are FAIL verdicts (the existing rule) and are counted and reported.
